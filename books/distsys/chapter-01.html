Chapter 1

System Models

A distributed-system claim is meaningful only after the participants, communication rules, timing assumptions, and possible failures have been stated.

1.A · Chapter abstract

A system model defines the participants in a distributed computation and the actions they may perform. It represents the system as processes, channels, and events, making local state and communication boundaries explicit.

Synchrony assumptions state what, if anything, is bounded in time. A failure model states how processes and channels may deviate from their intended behavior. Together, these assumptions determine which executions the theory must consider.

The chapter then defines admissible executions and separates safety and liveness. A payment example shows why a timeout is only an observation, how two different failures can produce the same visible history, and why a useful specification must prevent bad outcomes while still requiring progress.

Example Did the payment happen?

A customer submits order 81 with payment request key k. The checkout service forwards the charge to the payment service:

Browser 1 · Pay order 81 Checkout
Checkout 2 · Charge key k Payment
Payment commits charge kthe local state changes
Checkout 3 · Reply delayed Payment
Checkout times outno reply is not the same as no charge

The checkout service must decide whether to retry. A blind retry may charge twice; refusing to retry may leave a valid order unfinished. The right response depends on what channels can do, how the payment process can fail, and which outcomes the specification permits.

1.1

Processes, Channels, and Events

Terminology
System model
The declared rules for participants, communication, timing, failures, and the executions considered possible.
Process
One modeled participant with private local state and a sequence of steps.
Local state
The information currently stored by one process, including variables and protocol position.
Event
One indivisible modeled step, such as a local computation, message send, or message receive.
Channel
The modeled path by which one process sends messages to another.
Message
A value placed on a channel by a send event and made available by a corresponding receive event.
Local history
The ordered sequence of events observed by one process.

A process is a modeling unit, not necessarily an operating-system process. It may represent a server, a browser tab, a replica, a thread, or one protocol role. The useful boundary is the point at which state is local and interaction must be modeled explicitly.

Assumption Process boundaries are chosen by the model

If two components share memory and fail together, one model may treat them as one process. If their scheduling, state, or failures must be distinguished, the model can separate them. The choice should expose the behavior relevant to the claim.

Example · continued A send and a receive are different events

Checkout event c2 places charge(k) on a channel. Payment event p1 receives it. The interval between c2 and p1 can contain network delay, message loss, a partition, or a payment-process failure. Writing “checkout calls payment” as one atomic step would hide every one of those possibilities.

Invalid inference Sent does not mean received

A send event proves only that the sender performed its local action. Delivery requires a channel guarantee and, usually, a receiver that remains able to take steps.

Key result A global execution is constrained by local histories and communication

The model builds system-wide behavior from process-local event order plus relations between matching sends and receives. Any additional shared-state or atomicity claim must be stated explicitly.

Section summary
  • Processes own local state and observe local histories.
  • Channels connect distinct send and receive events.
  • Model boundaries determine which delays and failures remain visible.

1.2

Synchronous and Asynchronous Execution

Terminology
Time bound
A known finite upper limit on an action such as message delivery or process response.
Synchronous model
A model with known bounds on the timing quantities required by the algorithm.
Asynchronous model
A model with no known finite upper bound on process speed or message delay.
Partial synchrony
A model in which useful bounds exist only eventually, or exist but are initially unknown.
Timeout
A local event triggered after waiting for a chosen duration without receiving an expected observation.

Asynchronous does not mean that every message is slow. It means the algorithm cannot rely on a known deadline that every admissible delivery meets. A message that usually arrives in 20 milliseconds may still be delayed for 20 seconds in an admissible asynchronous execution.

Assumption State exactly what is bounded

A synchronous argument may require a delivery bound, a bound on process-step duration, bounded clock drift, or several of these. “The network is fast” is not a mathematical assumption.

Example · continued The same timeout has two compatible explanations
Observed prefixNo reply from payment by 2 seconds.
→
Slow executionPayment is correct; the reply arrives at 2.1 seconds.
Crash executionPayment crashed; no reply will arrive.

At the timeout event, checkout has the same local history in both executions. In an asynchronous model, it cannot decide from silence alone which execution it is in.

Failure case A timeout is suspicion, not proof of failure

Increasing the timeout may reduce false suspicions in a particular deployment, but no fixed duration creates a proof in a fully asynchronous model.

Key result Timing assumptions determine what silence can mean

With a valid known bound, missing the deadline can establish that some assumption was violated. Without such a bound, a process that has failed is indistinguishable from one that is merely delayed.

Section summary
  • Synchronous models expose usable time bounds; asynchronous models do not.
  • Partial synchrony captures systems that become predictably timed after disruption.
  • A timeout records elapsed local waiting, not remote failure.

1.3

Failure Models

Terminology
Correct process
A process that follows the algorithm for the duration required by the model.
Crash-stop
A process takes valid steps until it crashes, then takes no further steps.
Crash-recovery
A process may stop and later restart, possibly retaining only state written to stable storage.
Omission failure
An expected send, receive, or response does not occur.
Network partition
Communication between groups of processes is unavailable while processes on both sides may continue.
Byzantine failure
A faulty process may deviate arbitrarily, including sending conflicting or fabricated information.

A failure model is a set of allowed deviations. It does not predict which component will fail; it defines the behaviors a correct algorithm must tolerate. A crash-only proof does not automatically cover data corruption, duplicate execution, or a process that lies.

Channel behavior belongs in the model

Channels may be reliable or lossy, FIFO or reordering, duplicate-free or duplicating, authenticated or unauthenticated. “TCP” or “the network” is not a complete channel model: an application can reconnect, retry, duplicate a request, or fail between receiving bytes and recording their effect.

Example · continued Two crashes produce the same timeout and different states
Observed by checkout · no reply
ExecutionPayment’s last eventWas the card charged?What checkout sees
Crash before commitReceive charge(k)NoTimeout
Crash after commitPersist charge kYesTimeout

The retry decision cannot depend only on whether a reply arrived. A crash-recovery design normally pairs a unique request key with durable state so the recovered service can recognize the same operation.

Assumption Recovery requires a persistence contract

A crash-recovery model must say which writes survive, whether a write can be torn, and how a restarted process identifies its prior incarnation. “The process restarts” is incomplete without retained-state semantics.

Model mismatch A guarantee ends at the failure model’s boundary

An at-most-once argument based on durable request keys does not tolerate a Byzantine payment service that deliberately ignores the key. A partition-tolerant protocol may still fail if messages are silently corrupted and authentication was assumed.

Key result Fault tolerance is always conditional

A protocol tolerates a stated number and class of failures under stated channel and storage assumptions. Removing those qualifiers changes the claim.

Section summary
  • Failure models enumerate allowed deviations from the algorithm.
  • Crash-stop, recovery, omission, partition, and Byzantine behavior are not interchangeable.
  • Channel and persistence semantics are part of the failure model.

1.4

Executions and Admissibility

Terminology
Configuration
The complete modeled state at one point: every process’s local state and every channel’s contents.
Execution
An alternating sequence of configurations and enabled events, also called a run.
Schedule
The sequence specifying which enabled process or delivery event occurs next.
Prefix
A finite initial segment of an execution.
Admissible execution
An execution that satisfies the model’s timing, failure, channel, and fairness assumptions.
Fairness
A progress assumption excluding executions that postpone an eligible action forever without an allowed reason.

A configuration is a snapshot of the mathematical state, not necessarily something the running system can read atomically. An event transforms one configuration into the next.

C₀ —e₁→ C₁ —e₂→ C₂ —e₃→ ···
Example · continued One observed prefix, several admissible continuations

The prefix ending at checkout’s timeout is compatible with a delayed reply, a lost reply, a payment crash before commit, and a payment crash after commit. Which continuations are admissible depends on the declared channel and failure model—not on which continuation the implementer expects most often.

Assumption Fairness excludes artificial non-progress

If a correct process is continuously able to take a step, a weakly fair schedule eventually lets it do so. If a model promises reliable eventual delivery, it excludes a run that keeps one particular message in transit forever. Fairness is a stated restriction, not a consequence of asynchronous execution.

Proof error A successful trace is not a correctness argument

Showing one schedule in which the reply arrives demonstrates possibility. Correctness requires the property to hold for every admissible schedule, including inconvenient interleavings and failures.

Key result Correctness quantifies over all admissible executions algorithm A satisfies property P ⇔ every admissible execution of A satisfies P
Section summary
  • Executions alternate configurations and events.
  • Admissibility applies every assumption in the system model.
  • Correctness covers all admissible schedules, not representative tests.

1.5

Safety and Liveness Properties

Terminology
Property
A set of executions regarded as acceptable by the specification.
Invariant
A state predicate that holds initially and remains true after every allowed transition.
Safety
A property stating that a prohibited outcome never occurs.
Bad prefix
A finite execution prefix after which no continuation can repair a safety violation.
Liveness
A property stating that a required progress event eventually occurs.

The standard shorthand is useful: safety says “nothing bad happens,” while liveness says “something good eventually happens.” The sharper distinction is how violations appear. A safety violation has a finite witness. No finite amount of waiting alone disproves liveness, because the required event could still occur later.

Example · continued An idempotency key supports safety

The payment service stores the outcome under key k. A retry with the same key returns the stored outcome instead of creating a second charge.

Protocol · handle charge request k
  1. Read the durable record associated with k.
  2. If a completed outcome exists, return that same outcome.
  3. Otherwise, create the charge and the completed record as one atomic operation.
  4. Return the recorded result. A later retry starts again at step 1.

This protocol addresses duplicate requests only if storage preserves the key and the charge-record update is atomic with the external effect being controlled. Liveness still requires eventual delivery, retries, recovery, and an available payment path.

Assumption Liveness needs an environment that eventually cooperates

No algorithm can guarantee completion if every process may crash forever or every message may be dropped forever. A liveness statement therefore names the processes that remain correct and the fairness or eventual-timing conditions it needs.

Specification failure Safety alone permits a useless implementation

A service that never charges and never replies satisfies “never charge twice.” Conversely, a service that always replies “success” may be live but unsafe. A useful specification normally contains both kinds of property.

Key result Safety is preserved; liveness is pursued

Safety arguments commonly establish an invariant for every transition. Liveness arguments show that, under fairness and fault assumptions, the execution cannot postpone required progress forever.

Section summary
  • Safety violations have finite bad prefixes.
  • Liveness requires eventual progress and therefore depends on environment assumptions.
  • A useful distributed-system specification usually needs both.
1.6 · Applications

Where these ideas appear

These systems make their process, timing, and failure assumptions operational. Each mechanism is useful because its boundary is explicit.

Processes and crash recovery

Erlang/OTP

Erlang processes communicate through asynchronous signals. Links and monitors turn process termination into observable signals, while OTP supervisors restart selected child processes. This is a structured crash-and-recovery model; it does not make arbitrary faulty behavior safe.

Timeout-based suspicion

Kubernetes

Kubernetes probes convert repeated observations into policy. A failed readiness probe removes a Pod from service traffic; repeated liveness failures can trigger a restart. Probe intervals, timeouts, and thresholds are timing assumptions, and poor settings can mistake overload for failure.

Sessions under partition

Apache ZooKeeper

ZooKeeper maintains client sessions with heartbeats and a negotiated timeout. If the cluster hears nothing before expiration, it ends the session and removes its ephemeral nodes. The transition is authoritative for ZooKeeper even if the disconnected client process is still running.
