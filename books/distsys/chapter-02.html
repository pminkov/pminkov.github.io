Chapter 2

Time and Causality

A distributed system has no single observer and no universally available clock. Its ordering claims must be constructed from local events and exchanged information.

2.A · Chapter abstract

This chapter develops two ways to reason about the order of events in a distributed system. Physical clocks estimate when events occur, but oscillator drift and uncertain network delay prevent machines from observing one exact shared time.

Logical clocks instead describe causal order. Lamport clocks preserve happens-before, while vector clocks also identify concurrency. Causal histories expose the resulting partial order directly.

The final section uses consistent cuts and distributed snapshots to construct global states without simultaneous observation. Examples trace timestamp updates, compare vector values, and show how messages in transit become part of recorded channel state. Together, these tools separate physical precedence from causal dependence and make the assumptions behind ordering claims explicit.

Example Changing an address before placing an order

Replica P and replica Q are servers holding separate copies of the customer’s data. The customer’s browser talks to both of them:

Browser 1 · Change address Replica P
Browser 2 · Success + version 42 Replica P
Browser 3 · Order requires 42 Replica Q
Replica P Version 42 still in transit Replica Q
Replica Q waits for version 42then processes the order

Receiving step 2 is what it means for the customer to have observed the update: the system has confirmed it to the browser. The customer does not inspect either server.

The browser carries version 42 into step 3. That requirement is the causal context. Without it, Q may process the order immediately with the old address because P’s update is still in transit.

2.1

Physical Clock Assumptions

Terminology
Instant
One point in time. An instant has no duration; an interval is the span between two instants.
Reference time
An ideal timeline used by the mathematical model to compare clocks. Processes cannot read it directly.
Physical clock
A machine’s mechanism for estimating elapsed time and assigning time-of-day readings.
Clock reading
The value returned by a physical clock at a particular instant.

Each machine, or node, has a hardware clock driven by an oscillator. Here p names a process. Processes can share a machine, but a distributed-system model usually places them on separate machines; each process reads the clock of the machine on which it runs.

Let t denote an instant on the ideal reference timeline. The expression Cₚ(t) means “the value process p’s machine clock would show at reference instant t.” The model uses t to discuss accuracy. Process p can read Cp, but it cannot independently look up t.

Assumption Bounded clock drift

A common model assumes that every hardware clock’s rate differs from the reference rate by at most ρ. Without a drift bound, a clock could advance arbitrarily fast or slowly and no finite resynchronization schedule could bound its error.

1 − ρ ≤ dCₚ(t)/dt ≤ 1 + ρ
Terminology
Skew
The difference between two clock readings at the same reference instant.
Drift
The difference between clock rates. Drift causes skew to change over time.
Offset
The signed difference between one clock and a chosen reference clock.
skew(p,q,t) = |Cₚ(t) − Cq(t)|
Example · continued The address change happened first, but its timestamp says otherwise

Suppose P’s clock is 20 milliseconds ahead of reference time, while Q’s clock is 20 milliseconds behind. The events occur 10 milliseconds apart:

What actually happens
Replica P 1 Saves address P’s clock10:00:00.120
↓ 10 ms later in reference time
Replica Q 2 Receives order Q’s clock10:00:00.090
Wrong conclusion .090 < .120 “The order happened first.”

The clocks have not stopped working; each is simply offset from the other. The red conclusion is what fails: a smaller reading on a different machine does not necessarily mean an earlier event.

Physical timestamps can prove this order only when the known clock uncertainty is smaller than the separation between the events. The version token from the first example avoids that assumption: it tells Q directly that the order depends on the address update.

Synchronization over a network

Terminology
Round-trip delay
The elapsed client time from sending a request to receiving its reply, less time spent processing at the server.
Uncertainty
The range of clock offsets compatible with the observed timestamps and unknown one-way delays.

A client sends a request at local time t0. The server records receive and send times t1 and t2. The client receives the reply at t3. These four readings support an estimate of network delay and the server’s offset from the client.

delay ≈ (t₃ − t₀) − (t₂ − t₁) offset ≈ ((t₁ − t₀) + (t₂ − t₃)) / 2
Assumption Approximately symmetric network delay

The offset formula assigns half of the round-trip delay to each direction. If the request and reply experience substantially different delays, the estimate is biased.

Worked trace · one synchronization exchange
ReadingValueMeaning
t₀100Client sends request
t₁114Server receives request
t₂116Server sends reply
t₃126Client receives reply
Estimatedelay = 24, offset = +2Server clock appears 2 units ahead
Key result Synchronization produces a bounded estimate, not exact global time

Unknown one-way delay prevents the client from identifying one exact reference instant for the server’s reading. Correct systems retain an uncertainty bound or tolerate overlapping time intervals.

Section summary
  • An instant belongs to the model’s reference timeline; a clock reading is a machine’s estimate at that instant.
  • Skew measures disagreement now. Drift describes how that disagreement changes.
  • Network synchronization narrows uncertainty but does not create a perfectly shared clock.

2.2

Lamport Clocks

Terminology
Event
One indivisible step in the execution model, such as a local operation, message send, or message receive.
Happens-before
The smallest relation containing local process order and send-before-receive order, and closed under transitivity.
Concurrent events
Two events for which neither happens before the other.
Logical clock
A mechanism that assigns values to events to preserve an ordering relation, without estimating physical time.
Timestamp
The logical-clock value attached to an event or message.

The happens-before relation, written a → b, is built from three rules:

  1. If a and b occur on the same process and a occurs first, then a → b.
  2. If a sends a message and b receives that same message, then a → b.
  3. If a → b and b → c, then a → c.

A Lamport clock is one integer counter per process. It preserves happens-before by advancing on local work and carrying the current value with every message.

Protocol · Lamport clock update
  1. Before each local event, process p increments its counter: Lₚ ← Lₚ + 1.
  2. A sent message carries the sender’s new counter value.
  3. On receiving timestamp t, process q sets Lq ← max(Lq, t) + 1.
Example · continued The address dependency crosses machines without wall-clock time

Now give replica P, the customer’s browser, and replica Q Lamport counters. The success response and the later order request carry counter values from one process to the next:

EventLamport updateRecorded value
P saves the address16 + 117
P sends success17 + 118, carried to browser
Browser receives successmax(4, 18) + 119
Browser sends order19 + 120, carried to Q
Q receives ordermax(7, 20) + 121

The values preserve the chain address saved → success received → order received: 17 < 19 < 21. Clock offset cannot reverse it because no physical time-of-day readings are compared.

This does not make the new address appear at Q. The Lamport timestamp records order; the address version identifies the state Q must have. A system can carry both, or use an ordered replication log in which the address version is derived from the logical order. Q still waits until that required update has been applied.

Key result Lamport clock condition

If event a happens before event b, the Lamport timestamp of a is smaller than the Lamport timestamp of b.

a → b ⇒ L(a) < L(b)
Failure case The converse is not valid

From L(a) < L(b), one cannot conclude a → b. Two concurrent events can receive different Lamport timestamps because the counters compress too much history into one number.

To obtain a total order for log entries or tie-breaking, a system can compare pairs (L(a), process(a)). This orders every pair of events, but the process identifier adds administrative order rather than causal information.

Section summary
  • Happens-before is generated by local order, message delivery, and transitivity.
  • Lamport timestamps respect causality but do not identify concurrency.
  • A total order derived from timestamps is useful bookkeeping, not a proof of causation.

2.3

Vector Clocks

Terminology
Vector clock
A timestamp containing one counter per process in the model.
Component
One position in the vector, associated with one process.
Component-wise maximum
A vector formed by taking the larger value at each position.
Dominates
Vector X dominates Y when every component of X is at least the corresponding component of Y.

For n processes, process p stores a vector Vp of length n. The component Vp[i] summarizes how many events from process i are known to p. This retains enough information to distinguish causal order from concurrency.

Protocol · vector clock update
  1. Before a local event, p increments its own component Vₚ[p].
  2. A sent message carries the sender’s complete vector.
  3. On receipt, q takes the component-wise maximum of its vector and the message vector, then increments Vq[q].
Terminology Strict vector order

V(a) < V(b) when every component of V(a) is less than or equal to the corresponding component of V(b), and at least one component is strictly less.

V(a) < V(b) ⇔ (∀i, V(a)[i] ≤ V(b)[i]) and V(a) ≠ V(b)
Key result Vector clocks characterize happens-before exactly a → b ⇔ V(a) < V(b) a ∥ b ⇔ V(a) ≰ V(b) and V(b) ≰ V(a)
Limit Metadata grows with the participant set

A standard vector contains one component per process. Large or changing memberships therefore require variants such as version vectors, dotted version vectors, interval tree clocks, or application-specific dependency sets.

Section summary
  • Each vector component summarizes one process’s known progress.
  • Comparable vectors identify causal order; incomparable vectors identify concurrency.
  • The additional information improves precision but increases metadata cost.

2.4

Causal Histories

Terminology
Causal history
The set of events known to precede an event. In this section, H(e) also includes e itself.
Partial order
An ordering in which some pairs are comparable and others are not.
Causal path
A chain of local-order or message edges connecting one event to another.
Dependency
A relation indicating that one event may rely on information produced by another.

Let H(e) denote the causal history of event e. A direct representation could attach a unique identifier for every known prior event. Then set inclusion would expose order: if H(a) is a proper subset of H(b), b includes everything known at a and at least one additional event.

Invalid inference Concurrent does not mean simultaneous

Concurrent events need not occur at the same physical instant. It means only that the model has no causal path in either direction. One may occur earlier in wall-clock time without being able to influence the other.

From histories to compact metadata

Full histories grow by one identifier per event. Vector clocks compress the same information when events belong to a fixed set of sequential processes. A component value k represents a known prefix: knowing event pk implies knowing p1 through pk−1.

Operational consequence Concurrent updates have no causally selected winner

If two updates are concurrent, neither was created with knowledge of the other. A replicated system must preserve both, merge them, or apply an explicit conflict rule. Causality alone cannot choose one.

Section summary
  • A causal history makes the dependencies of an event explicit.
  • The resulting order is partial because concurrent pairs remain incomparable.
  • Vector clocks compress causal histories by representing known process prefixes.

2.5

Global States and Cuts

Terminology
Local state
The variables and execution position recorded by one process.
Channel state
The messages sent but not yet received across one communication channel.
Global state
One local state per process together with all channel states.
Cut
A boundary selecting one prefix of events from each process history.
Snapshot
A recorded global state intended to represent one possible point in a distributed execution.

Processes do not need to pause at the same physical instant to define a global state. A cut selects how far into each local history the snapshot extends. The selected local prefixes determine the process states; messages crossing the boundary determine the channel states.

Terminology Consistent cut

A cut is consistent when it is closed under happens-before. If the cut contains an event, it must also contain every causal predecessor of that event.

b ∈ C and a → b ⇒ a ∈ C
AllowedSend included, receive excluded. The message is recorded in the channel state.
Not allowedReceive included, send excluded. The snapshot contains an effect without its cause.
Failure case An inconsistent cut cannot describe a reachable execution prefix

A receive event depends on its send event. Recording the receive without the send violates closure under happens-before.

Distributed snapshots

Assumption Chandy–Lamport channel model

The basic snapshot protocol assumes reliable, directed FIFO channels: messages are not lost, and messages from one sender arrive on a channel in send order.

Protocol · record a distributed snapshot
  1. The initiator records its local state and sends a marker on every outgoing channel before sending later application messages.
  2. On receiving its first marker, a process records its local state, records that incoming channel as empty, and forwards markers on its outgoing channels.
  3. For every other incoming channel, the process records arriving application messages until that channel’s marker arrives. Those messages form the channel state.
  4. The snapshot is complete when every process state and every incoming channel state has been recorded.
Terminology Stable property

A property that remains true once it becomes true. Termination and deadlock are standard examples under the appropriate system model.

Key result A consistent snapshot supports global reasoning without a shared physical clock

The marker protocol reconstructs a consistent global state from local observations. Its correctness comes from causal and channel-order reasoning, not from simultaneous clock readings.

Section summary
  • A global state includes both process state and messages in transit.
  • A consistent cut contains every cause of every event it contains.
  • Snapshot protocols record consistent states without stopping all processes at one physical instant.
2.6 · Applications

Where these ideas appear

These systems make different choices about time and order. The point is not that they implement the chapter identically, but that each turns one of its concepts into an operational mechanism.

Bounded physical time

Google Spanner

TrueTime reports an interval containing the possible current time. Spanner assigns transaction timestamps and waits out the remaining uncertainty before exposing a commit. This lets externally consistent transaction order agree with the order clients observe.

Spanner documentation ↗
Partition-local order

Apache Kafka

Kafka assigns sequential offsets inside each totally ordered partition. Consumers and replicas follow that log order instead of comparing machine clocks. Different partitions do not form one global order, so related events are commonly routed by key to the same partition.

Kafka documentation ↗
Causal context

MongoDB

Causally consistent sessions track operation time and cluster time across requests. With majority read and write concerns, a dependent read can wait until the receiving server has reached the required cluster time—the same shape as carrying version 42 to replica Q.
