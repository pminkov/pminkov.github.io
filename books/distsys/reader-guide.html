Structure

Chapter organization

The book develops each topic from model to consequence. Definitions are introduced before algorithms that depend on them, and guarantees are stated together with the assumptions under which they hold.

The prose is compact and literal. Terms are defined before use, and an analogy never substitutes for the underlying model. Examples focus on executions, state transitions, and counterexamples.

Chapter abstract

Every chapter begins with one compact abstract. It is a first-class destination in the chapter navigation and table of contents, labeled N.A so the technical sections can retain their existing numbers. It should prepare the reader without requiring knowledge of the chapter’s notation or proofs. The abstract states the problem, names the main conceptual route, and identifies the conclusion or capability the chapter develops. Two or three short paragraphs separate those parts, while selective bold text exposes the terms that organize the chapter.

N.A · Chapter abstract

This chapter develops two ways to reason about the order of events in a distributed system. Physical clocks estimate when events occur, but oscillator drift and uncertain network delay prevent machines from observing one exact shared time.

Logical clocks instead describe causal order. Lamport clocks preserve happens-before, while vector clocks also identify concurrency. Causal histories expose the resulting partial order directly.

The final section uses consistent cuts and distributed snapshots to construct global states without simultaneous observation. Examples trace timestamp updates, compare vector values, and show how messages in transit become part of recorded channel state. Together, these tools separate physical precedence from causal dependence and make the assumptions behind ordering claims explicit.

  • 100–160 wordsLong enough to map the argument; short enough to read before committing to the chapter.
  • Two or three paragraphsSeparate the problem, conceptual route, and outcome instead of presenting one dense block.
  • Self-containedNo unexplained symbols, citations, proof steps, or references to figures not yet seen.
  • Selective emphasisBold three to six terms that carry the structure of the chapter; do not emphasize full sentences.

Applications

Every chapter ends with a numbered Applications section immediately after its final theory section—for example, Chapter 2 uses 2.6. It contains three real-world systems that use, approximate, or deliberately limit the concepts developed in the chapter. Each entry names the relevant concept, describes one concrete mechanism, states an important boundary when needed, and links to primary technical documentation. These entries connect theory to implementation; they are not product recommendations.

Local before globalStart with what one process can observe, then construct system-wide claims.
Assumptions stay visibleTiming, failure, and channel assumptions appear near the claim they support.

Conventions

Visual language

Color identifies six recurring kinds of information. Every colored element also has a written label and a distinct border, so color is never the only cue.

Terminology Clock skew

The difference between two clock readings taken at the same reference instant.

Assumption Reliable FIFO channels

Messages are not lost, and each sender’s messages arrive in the order sent.

Key result Lamport clock condition

If a → b, then L(a) < L(b). The converse does not necessarily hold.

Failure case Timestamp order is not causality

L(a) < L(b) alone does not prove that event a could have influenced event b.

Example Changing an address before placing an order

A customer updates an address at replica P and receives a success response containing a version token. When the next order reaches replica Q, the token tells Q to wait until it has applied that address version. The example makes causal context concrete before introducing the formal model.

N.X · Applications From concept to deployed system

Three entries at the end of a chapter connect its theory to concrete mechanisms in real systems. Each entry identifies the relevant concept, explains the mechanism briefly, and links to a primary source.

Use rule: a terminology box appears at the first substantial introduction of a term. Later uses rely on normal text or a compact notation reminder rather than repeating the full box.
Example rule: begin with concrete actors and an observable problem, then connect the scenario to the formal concept it motivates. An example illustrates a mechanism or failure mode; it does not establish a guarantee.
Applications rule: include exactly three real systems at the end of a chapter. Prefer systems that make distinct design choices, describe only the mechanism relevant to the chapter, name important scope limits, and cite official documentation or a primary paper.

Traces and protocols

Neutral elements carry procedural material. A worked trace records how state changes across events. A protocol block lists the actions a process performs.

Section summary
  • Traces explain a specific execution.
  • Protocols specify behavior for every admissible execution.
  • A trace illustrates a protocol; it does not prove the protocol correct.

Graphics

Reading diagrams

Unless a figure says otherwise, time advances from left to right. Horizontal lanes represent processes or nodes. Arrows between lanes represent messages or causal dependencies, not physical distance.

Filled node
Event included in the current state or cut.
Hollow node
Event outside the current state or cut.
Directed arrow
Message flow or dependency from cause to effect.
Vertical line
A cut across distributed execution histories.
Process colors: colors distinguish lanes within one figure. The labels P, Q, and R carry the meaning; green does not permanently refer to a particular kind of process.

Notation

Symbols appear in a compact reminder when their meaning may not be immediate. Formal definitions remain in the main text.

  • a → bEvent a happens before event b.
  • a ∥ bEvents a and b are concurrent.
  • Cₚ(t)The clock read by process p at ideal reference time t.
  • V(a)The vector timestamp associated with event a.
